# Harness 릴리스·장애·검증 이력

## 목적과 기록 규칙

이 문서는 사용자에게 배포한 Harness 설치본에서 발생한 문제와 조치를 추적한다. 다음 항목을 한 건으로 기록한다.

- 발생 증상과 영향 범위
- 확인한 원인과 근거
- 변경한 파일·동작 및 안전성 판단
- 자동·수동 검증 결과
- 배포 버전, SHA-256, 커밋, 후속 조치

새 기능, 장애 수정, 설치·업데이트 동작 변경은 배포 전에 이 문서를 갱신한다. 확인되지 않은 추정은 원인으로 기록하지 않는다.

## 2026-08-30 · Manager 실행·설치 경로 복구

| 항목 | 기록 |
|---|---|
| 증상 | Manager 실행 시 검은 PowerShell 창이 잠깐 표시된 뒤 Manager가 보이지 않거나, 시작 메뉴 바로가기가 예상한 설치 폴더를 가리키지 않았다. |
| 원인 1 | Windows PowerShell 5.1이 BOM 없는 UTF-8 `manager.ps1`을 `-File`로 읽을 때 한글 UI 문자열을 잘못 해석했다. |
| 원인 2 | Manager의 두 열 체크박스 좌표 계산이 Windows PowerShell 5.1의 `New-Object` 인수 해석과 충돌했다. |
| 원인 3 | 테스트 설치가 데모 설치와 같은 Inno Setup AppId를 사용해 시작 메뉴 바로가기와 설치 등록 정보가 임시 테스트 폴더로 바뀌었다. |
| 조치 | 배포 번들의 Manager를 UTF-8 BOM으로 생성하고, 좌표 계산을 호환 방식으로 변경했다. 시작 메뉴는 `-WindowStyle Hidden`으로 Manager만 보이게 한다. Demo 5를 기본 설치 폴더에 재설치해 바로가기와 등록 정보를 복구했다. |
| 재발 방지 | `TestBuild`는 데모·정식 배포와 다른 AppId 및 `VibeCodeHarness-Test` 폴더를 사용한다. 실제 사용자 설치 AppId로 격리 테스트를 하지 않는다. |
| 검증 | 기본 설치 폴더의 바로가기 대상·인수·작업 폴더 확인, UTF-8 BOM 확인, Manager 3초 실행 유지, 표준 오류 0바이트, 번들 검증 성공. |

## 2026-08-30 · 승인 매니페스트 기반 업데이트 정리 구현

| 항목 | 기록 |
|---|---|
| 문제 | 같은 설치 위치에 새 EXE를 실행하면 이름이 같은 파일만 덮어쓰므로, 새 번들에서 제거된 과거 하네스 파일이 남았다. 그 상태에서는 새 번들의 정확한 무결성 검증도 실패할 수 있다. |
| 구현 | 설치기가 파일을 덮어쓰기 전에 기존 `bundle.manifest.json`을 설치 폴더 밖 임시 위치에 보관한다. 새 번들 추출 후 `gg bundle cleanup`이 이전·새 매니페스트를 비교하여 이전에만 있던 파일만 대상으로 삼는다. |
| 삭제 조건 | 이전 매니페스트와 새 매니페스트는 모두 기관 신뢰 공개키로 Ed25519 서명이 검증되어야 한다. 새 번들의 모든 현재 파일은 검증되어야 하며, 추가 파일은 이전 승인 목록에서 제거 대상으로 확인된 파일만 허용된다. 예상 밖 파일·변조·신뢰되지 않은 서명이 있으면 삭제하지 않고 설치를 중단한다. |
| 사용자 수정 보호 | 제거 대상 파일이 이전 승인본과 다르면 먼저 설치 폴더 밖 `.vibecode-harness-update-backups`에 복사한 후 제거한다. 프로젝트 폴더와 Inno 제거 프로그램 파일은 대상이 아니다. |
| 사용자 흐름 | EXE는 GitHub에서 자동으로 최신 파일을 내려받지 않는다. 사용자는 포털에서 새 승인 EXE를 내려받아 기존 설치 위치에 실행한다. 설치가 성공하면 옛 하네스 파일까지 정리되고 새 번들이 재검증된다. |
| 검증 | 자동 테스트 70건 통과: 승인된 제거 파일 삭제, 사용자 수정 파일의 외부 백업, 예상 밖 추가 파일에서 삭제 없는 실패를 확인했다. 격리된 `TestBuild`에서 기존 번들 설치 → 새 번들 EXE 업데이트 → 최종 번들 검증 → 제거까지 모두 성공했다. |
