# 47차 — 체커 0.6 계약 정렬 · 훅 우회 차단 · lock 무결성 (2026-11-03)

## 1. 왜 바꿨나

2026-11-03 세 저장소(체커·포털·하네스)를 함께 점검하면서 하네스가 **체커 0.5 시절 가정**에 머물러 있는 것이 확인됐다.

| 발견 | 결과 | 근거 |
|---|---|---|
| `gg verify --local-checker` 가 `--check-deps` 를 박아 호출 | 체커 0.6 에서 이 옵션은 `--deps online`(외부 조회) 별칭이다. 폐쇄망 PC 에서도 외부 조회를 시도하고, 0.6 의 로컬 기본값·위협정보 신선도 게이트를 우회했다 | `bin/gg.mjs` runChecker, 체커 `cli.py _requested_deps_mode` |
| 종료코드 0 이 아니면 전부 `blocked` | 체커가 "위협정보가 없어 패키지를 보지 못했다"(종료 3, `undetermined`)고 말해도 영수증은 '차단'이라 적었다. 검사하지 못한 것과 막힌 것은 다른 사실이다 | `lib/checker-evidence.mjs` |
| 체커 버전을 확인하지 않음 | 0.6 아래 체커는 옵션 없이는 패키지를 전혀 보지 않는다 — 조용한 초록불 | `checkerCommand` 는 존재만 확인 |
| `gg package check` 가 종료코드 ≠ 0 을 전부 차단 | 체커 `check-package` 는 '취약'과 '판정 불가'를 둘 다 1 로 낸다. 위협정보 없는 PC 에서는 모든 패키지가 '차단'으로 보였다 | `packageCommand` |
| 훅 matcher 가 `Write|Edit|MultiEdit|Bash` | Windows Claude Code 의 PowerShell 도구와 NotebookEdit 는 훅을 거치지 않았다 | `CLAUDE_HOOK_MATCHER` |
| `.json` 은 허용 확장자, lock 지문은 "있을 때만" 검사 | AI 가 `.claude/settings.json` 에서 훅을 지우거나 lock 에서 지문 필드를 지우면 그 뒤로 아무것도 막히지 않았다 | `policyCheck`, 훅 |
| 설치 명령 탐지가 4가지 | `npm i`, `npm ci`, `uv`, `poetry`, `pipx`, `bun` 이 통과했다 | `isDirectPackageInstall` |
| 계약 문서가 "체커에 판정 필드 없음" 전제 | 체커는 0.5.4 부터 `gate.verdict` 를 낸다 | `checker-contract.yaml` v1.1 |

세 시스템이 같은 표를 보지 않아서 생긴 일이라, **표는 체커가 낸다**(`gvskb status --json` → `gate_contract`, 0.6.1). 하네스는 그 표를 `lib/checker-evidence.mjs` 의 `CHECKER_STATUS_BY_VERDICT` 로 옮겨 적고, 체커 저장소의 테스트가 두 표를 대조한다.

## 2. 바뀐 것

### 체커 연동 (`bin/gg.mjs`, `lib/checker-evidence.mjs`)

- **버전 하한 0.6.0** (`MIN_CHECKER_VERSION`). verify·package check·doctor 가 먼저 `gvskb status --json` 을 부른다. 미달이면 검사를 시작하지 않고 `incomplete`(41). `status` 가 없는 옛 체커는 `gvskb version` 으로 폴백한다.
- **호출 인자**: `--check-deps` 제거. `--deps` 는 넘기지 않는다(체커 기본 local, 기관은 `GVSKB_DEPS_MODE`). `--include-installed`·`--env`·`--fail-on block` 유지.
- **상태 결정**: `gate.verdict` 가 1차. approved·conditional → `review_required`, blocked → `blocked`(40), undetermined → `undetermined`→ verify 는 `incomplete`(41) 로 끝내고 사유(위협정보 없음이면 반입 안내)를 적는다. 종료코드는 교차 확인이며 어긋나면 `checker_status_conflict` 를 남기고 더 나쁜 쪽을 쓴다. 모르는 verdict 는 undetermined.
- **영수증 필드 추가**: `checker_version`, `checker_conditional_criteria`, `checker_intel_gap`, `checker_dependency_check{mode, requested_mode, packages_parsed, intel_state, intel_as_of, intel_age_days, auto_refresh_ok}`, `checker_status_conflict`, `checker_env`, `checker_status_source`. `final_verdict` 는 변함없이 `review_required`.
- **`gg package check`**: JSON 으로 나눈다. `checked=false` → `incomplete`(41, `check_mode` 기록) · 악성·거부·미존재·KEV·취약 → `blocked`(20) · `requires_review` → `review_required` · 그 외 `passed`.
- **`gg doctor`**: 체커 버전·위협정보 상태(`intel.state/as_of/age_days`)·서명 정책을 보이고, 버전 미달이면 `checker_update_required`(41), 위협정보 없음이면 "패키지 검사가 전부 판정 불가가 됩니다" 경고.
- **`checker_env`**: `institution-profile.yaml` `security.checker_env` 블록의 `GVSKB_*`·`PYTHON*` 키를 체커 환경변수로 강제한다(폐쇄망: `GVSKB_MODE: offline`, `GVSKB_INTEL_REQUIRE_SIGNATURE: "1"`, `GVSKB_INTEL_DIR`). 기본은 비어 있다. 프로파일 사본은 lock 지문으로 보호된다.
- lock: `checker_machine_verdict: "gate_v1"`, `checker_status_by_verdict`, `min_checker_version`. `gg update` 가 구 lock 의 `pending_upstream_machine_verdict` 를 올린다.

### 훅·우회 차단 (`bin/claude-pre-tool.mjs`, `lib/policy-engine.mjs`)

- matcher `Write|Edit|MultiEdit|NotebookEdit|Bash|PowerShell`. 옛 matcher 로 남은 등록은 `gg update` 가 `migrated` 로 넓힌다(다른 훅과 섞인 항목은 남의 matcher 를 건드리지 않고 우리 훅만 새 항목으로 옮긴다).
- **보호 경로**: `.vibecode-harness/`, `.claude/settings.json`, `.claude/settings.local.json`, `.githooks/`, `.github/workflows/vibecode-harness.yml`, `harness.lock.json`. Write·Edit·NotebookEdit 는 경로로, Bash·PowerShell 은 "보호 경로 언급 + 쓰기 동사·리다이렉트" 로 막는다(`protectedPathFailure`, `protectedPathCommandFailure`). 읽기(`cat`, `Get-Content`, `type`, `git diff`)는 통과.
- 설치 탐지 확장: `npm i|ci|install-ci-test|exec|x`, 플래그가 앞에 와도(`npm -g i`, `npm --prefix . install`), `pnpm i|add|dlx`, 인자 없는 `yarn`, `bun add|install|i`, `bunx`, `pipx install`, `py -m pip install`, `uv pip install|add|sync|tool`, `poetry add|install`, `pipenv install`, `conda install`. 승인되지 않은 런타임에 `deno`, `bun`, `perl`, `lua` 추가.
- **lock 지문 전수 검사**: `policy_sha256`·`institution_profile_sha256`·`package_policy_sha256`·`policy_profiles_sha256`·`runner_sha256`·`release_integrity_sha256`·`policy_engine_sha256`·`checker_evidence_sha256`·(claude 도구) `claude_hook_sha256` 가 lock 에 **없으면 실패**("lock 이 구버전입니다 — gg update"). `policy_profile` 이 `runtime_profile` 과 어긋나면 실패(트랙 변경은 `gg migrate` 로만).

## 4. 남은 한계 (솔직히)

- **설계 확인 자가 날인**: `gg design --confirm` 은 사람 확인 없이 영수증을 쓴다. AI 가 스스로 찍을 수 있다. 사람 확인과 묶는 절차(또는 포털 측 확인)가 필요하다.
- **`--no-verify` 우회**: pre-commit 은 `verify --hook`(테스트 deferred·체커 없음)이고 `--no-verify` 로 건너뛸 수 있다. 막는 것은 CI 필수 체크 지정뿐이며 그것은 아직 미실행이다(docs/25 §3).
- **번들 신뢰 루트가 설치 폴더 안**: `shared/trust/approved-signers.json` 이 번들과 같은 폴더에 있어 설치 폴더에 쓸 수 있는 공격자는 신뢰 파일과 manifest 를 함께 바꿀 수 있다. 신뢰 루트를 설치 폴더 밖(HKLM·기관 배포 경로)으로 옮겨야 한다. `signerFor` 는 `scope`(demonstration-only)도 보지 않는다.
- **보호 경로 명령 판정은 휴리스틱**: 변수로 경로를 조립하거나 스크립트 파일에 담아 실행하면 훅은 못 본다. 남은 우회는 `gg verify` 의 lock 지문 검사와 CI 가 받는다 — 그래서 지문 전수 검사를 이번에 함께 넣었다.
- **훅이 Bash 의 파일 쓰기 언어를 보지 않음**: `echo … > x.go` 는 훅을 통과하고 verify 에서 잡힌다(기존과 같음).
- **CI 템플릿**: 여전히 `ubuntu-latest` 이고 체커 단계가 없다(승인 Windows 러너 미지정, 체커는 포털 서버가 최종).
- **포털 제출 자동화 없음**: `verify` → `ready_for_portal_scan` 까지만. 포털 제출(`clients/report`)은 포털 측 API 와 함께 결정해야 한다.
