# 화면을 보며 설계하는 흐름

## 1. 왜 화면부터 보는가

공무원은 DBMS, 권한 모델, API보다 “어떤 화면에서 무엇을 입력하고 어떤 결과를 보는가”를 더 쉽게 판단한다. 따라서 하네스는 요구사항을 듣고 곧바로 구현하지 않는다. 먼저 실제 비율과 문구가 보이는 HTML 화면 시안 또는 승인된 디자인 도구 시안을 만든다.

화면 시안은 마케팅용 그림이 아니라 기능 검증 도구다. 화면마다 입력, 처리, 출력, 저장, 권한, 오류 상황을 확인한다.

## 2. 기본 산출 순서

```text
업무 설명
  -> 화면 목록과 사용자 흐름
  -> 핵심 화면 시안
  -> 화면별 기능·입력·결과 확인
  -> DB·관리자·권한 필요성 질문
  -> 화면 기능 설계 확정
  -> 구현
```

## 3. 화면별 확인 카드

모든 화면은 아래 다섯 칸을 함께 만든다.

| 항목 | 사용자가 확인하는 질문 |
|---|---|
| 목적 | 이 화면에서 무엇을 끝내나요? |
| 입력 | 무엇을 선택하거나 입력하나요? |
| 처리 | 누르면 어떤 작업이 진행되나요? |
| 결과 | 무엇을 확인·저장·제출하나요? |
| 예외 | 비어 있음, 오류, 권한 없음일 때 어떻게 보이나요? |

## 4. DB 필요성 판정

사용자에게 “PostgreSQL이 필요한가요?”라고 묻지 않는다. 다음 답으로 결정한다.

| 업무 답변 | 설계 판단 |
|---|---|
| 닫으면 내용이 사라져도 된다 | DB 없이 구현 |
| 내 PC에서만 다시 열면 된다 | 로컬 파일·SQLite 검토 |
| 여러 사람이 같은 목록을 보고 바꾼다 | 서버 DB와 동시성·권한 설계 |
| 기록을 몇 년간 찾아야 한다 | DB, 검색, 보존 정책 설계 |
| 결재·승인·삭제 이력이 필요하다 | DB와 감사 로그 필수 |

## 5. 관리자 화면 필요성 판정

관리자 화면은 기본값이 아니다. 아래 중 하나라도 필요하면 화면 목록에 추가한다.

- 담당자가 다른 사용자의 처리 대기·오류·완료 현황을 봐야 한다.
- 사용자별 권한, 승인, 차단, 역할 변경이 필요하다.
- 반복 오류, 보안 점검 집계, 보고서 제출 현황을 관리해야 한다.
- 운영 데이터의 수정·삭제 이력을 남겨야 한다.

그렇지 않으면 관리자 기능을 만들지 않고 사용자 화면을 단순하게 유지한다.

## 6. 시각 검토 게이트

`gg design`은 다음을 충족해야 통과한다.

1. 첫 화면, 핵심 작업 화면, 결과 화면이 있다.
2. DB 또는 관리자 기능이 필요하면 해당 화면도 있다.
3. 사용자가 시안에서 문구·순서·버튼·저장 위치를 확인했다.
4. 구현 전에 미결 업무 질문이 기록됐다.

L1은 HTML 파일을 브라우저로 열어 확인하는 방식이 기본이다. L2 이상은 화면 시나리오와 기능 설계를 함께 보관한다. Figma 등 디자인 도구는 선택 사항이며, 실제 구현과 분리되지 않도록 화면 구조·문구·상태를 같은 설계 파일에 기록한다.

화면이 없는 배치 자동화·CLI 도구는 `no_visual_interface` 예외를 사용할 수 있다. 이때는 화면 시안 대신 입력 예시, 실행 명령, 예상 출력, 오류 메시지, 저장 위치를 사용자가 확인해야 한다. 예외 사유와 확인 내역이 없으면 화면 검토를 건너뛸 수 없다.
