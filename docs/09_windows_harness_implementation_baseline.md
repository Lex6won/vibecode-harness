# Windows 실행형 바이브코드 하네스: 구현 기준선

## 1. 확정 목적

바이브코드 하네스는 보안 게이트웨이가 아니다. 공무원이 AI 코딩 도구로 업무 도구를 만들 때 다음 흐름을 **쉽게 설치하고 실제로 적용**하게 하는 Windows용 실행 환경이다.

1. 업무 목적과 사용자를 질문으로 정리한다.
2. 화면, 기능, 데이터, 관리자 필요성을 화면 시안으로 확인한다.
3. 승인된 개발 언어와 실행 환경 하나를 프로젝트에 적용한다.
4. 구현과 테스트를 진행하되, 새 패키지와 위험한 변경은 확인 절차를 거친다.
5. 개발 중에는 체커 MCP로 조언을 받고, 완료 전에는 체커 CLI로 전체 점검한다.
6. 결과와 결정만 증적으로 남기고, 원본 소스와 보고서는 사용자 PC에 보관한다.

`vibecode-checker`는 위 5번을 맡는 외부 검사 엔진이다. 하네스는 체커를 수정하거나 체커의 판정 논리를 복제하지 않는다.

## 2. 사용자에게 보이는 최종 흐름

### 2.1 최초 설치

1. 사용자는 경기도 바이브 코딩 지원 포털에서 코드서명된 `VibeCode Harness for Windows` 설치 파일을 받는다. GitHub는 개발 소스와 승인된 릴리스 자산의 보조 배포처이며, 일반 사용자의 기본 경로는 포털이다.
2. 브라우저의 설치 버튼은 설치 파일을 내려준다. 브라우저가 사용자 PC에 프로그램을 자동 설치하거나 파일을 제어하지 않으며, 사용자가 내려받은 설치 파일을 실행해 설치를 승인한다.
3. 설치기는 사용자별 경로에 하네스 실행기, 승인된 체커 번들, 필요한 내장 런타임을 설치한다. 상시 실행되는 로컬 에이전트나 브라우저의 localhost 제어 API는 만들지 않는다.
4. Python, Node.js, Git이 없는 PC도 기본 점검과 하네스 명령을 실행할 수 있어야 한다. `gg`는 내장 런타임으로 실행하고, 체커는 승인된 독립 실행 번들 또는 내장 Python 런타임으로 실행한다. Git은 Git 훅과 저장소 작업이 필요할 때 설치 또는 경로 선택을 안내한다.
5. Codex CLI, Claude Code, ChatGPT/Codex 데스크톱, Claude Desktop은 하네스 설치 대상이 아니라 별도 AI 도구다. 설치기가 도구 존재 여부를 확인하고, 없는 도구는 공식 설치 경로를 안내한다. 도구가 설치된 뒤에만 해당 어댑터·MCP 설정을 적용한다.
6. 설치기는 공식 번들의 서명, 해시, 최소 허용 버전을 확인한 뒤에만 설치한다.
7. 완료 화면에는 설치된 하네스·체커 버전, 적용 위치, 다음 행동인 "프로젝트에 적용"만 표시한다.

기본 설치는 관리자 권한을 요구하지 않는 사용자별 설치다. 기관 공통 배포가 필요할 때만 별도 MSI/Intune 방식의 관리자 설치를 제공한다.

### 2.2 프로젝트 적용

사용자는 프로젝트 폴더에서 한 번만 `gg init`을 실행하거나, 포털에서 내려받아 설치한 하네스의 실행 화면에서 프로젝트를 선택한다.

초기화 과정에서 반드시 정하는 값은 다음 네 가지다.

| 결정 | 사용자 선택 | 하네스 동작 |
|---|---|---|
| AI 도구 | Codex, Claude Code, 둘 다 | 해당 도구 지침·어댑터를 적용한다. |
| 개발 트랙 | Python 내부업무, Node.js 웹, TypeScript 웹 | 하나의 트랙과 승인 런타임을 잠근다. |
| 성숙도 | L1 안내, L2 검증, L3 릴리스 준비 | 요구 증적과 강제 수준을 정한다. |
| 프로젝트 종류 | 새 프로젝트, 기존 프로젝트 | 기존 프로젝트는 현황 진단과 예외 검토부터 시작한다. |

"둘 다"는 Codex와 Claude Code가 같은 정책과 증적을 읽는다는 뜻이며, 두 AI 도구를 설치한다는 뜻은 아니다. 데스크톱 도구의 MCP 설정은 제품·버전별 설정 형식이 다르므로, 어댑터가 해당 버전을 지원하고 설정 파일 위치를 검증한 경우에만 적용한다.

### 2.3 개발 흐름

| 단계 | 사용자 경험 | 실행 결과 | 다음 단계 조건 |
|---|---|---|---|
| 시작 | 쉬운 업무 질문에 답한다. | 기능 요약과 미결 질문 | 업무 목적·사용자·결과가 정리됨 |
| 설계 | 화면 시안과 기능을 보고 수정·확인한다. | PRD, 화면·기능 명세, DB·관리자 결정 | 화면 확인 기록 |
| 구현 | 선택된 언어·런타임으로 개발한다. | 변경 파일과 패키지 기록 | 정책·패키지 기준 충족 |
| 검증 | 테스트와 체커 점검을 실행한다. | 테스트·체커 증적 | 누락·차단 없음 또는 사람 검토로 이관 |
| 이관 준비 | 보고서와 SBOM을 확인한다. | 이관 요청 증적 | 사람 승인 |

DB, 관리자 화면, 개인정보, 외부 API, 권한 기능은 기본값이 아니다. 설계 질문에서 필요성이 확인될 때만 시안과 구현 범위에 추가한다.

### 2.4 개인정보와 프롬프트 처리

하네스는 프롬프트 원문을 기관 서버에 저장하지 않는다. `gg start`·`gg design`이 만드는 기획·설계 증적에는 개인정보·비밀값 패턴 검사를 적용하고, 감지되면 저장을 중단하고 범주형 표현으로 바꾸도록 안내한다.

Codex·Claude Code·데스크톱 앱에 사용자가 직접 입력하는 모든 대화 프롬프트를 하네스가 기술적으로 가로채는 것은 도구마다 가능 범위가 다르며, 이를 보장한다고 주장하지 않는다. 따라서 다음을 함께 적용한다.

1. 하네스 지침과 화면에서 개인정보·비밀값 입력 금지를 명시한다.
2. 생성·수정된 소스, 하네스 증적, 체커 보고서에서 알려진 비밀값·개인정보 패턴을 점검한다.
3. 기관망에서 외부 AI 서비스로 나가는 개인정보를 막아야 하는 경우에는 하네스가 아니라 기관 DLP·CASB·방화벽 정책을 적용한다.
4. 원본 프롬프트·소스·압축파일·보고서 본문은 포털에 전송하지 않는다.

## 3. 강제의 정확한 의미

하네스는 AI의 행동을 절대적으로 통제한다고 주장하지 않는다. 강제는 다음 세 지점의 조합이다.

| 지점 | 역할 | 우회 가능성 | 최종 처리 |
|---|---|---|---|
| Codex 지침·Claude Hook | 개발 중 즉시 안내·차단 | 다른 터미널·편집기로 우회 가능 | Git·CI에서 재검증 |
| 로컬 `gg build`·`gg verify` | 언어, 런타임, 패키지, 테스트, 체커 증적 확인 | 사용자가 명령을 실행하지 않을 수 있음 | Git 훅과 CI에서 실행 |
| 기관 저장소 CI·보호 브랜치 | 깨끗한 환경에서 재실행하고 병합 차단 | 로컬 관리자·저장소 관리자만 우회 가능 | 승인·감사 대상 |

따라서 개인 PC에서의 "강제"는 개발 단계의 안내와 빠른 차단이고, 조직 차원의 "강제"는 승인 번들, PR CI, 보호 브랜치로 완성된다. `git commit --no-verify`를 막는 유일한 방법은 필수 CI와 직접 main 푸시 금지다.

## 4. 개발 언어와 환경 제한

기관 기본 트랙은 아래 셋으로 확정한다.

| 트랙 | 허용 구현 언어 | 승인 실행 환경 | 기본 용도 |
|---|---|---|---|
| `python_internal` | Python | 승인 Python 런타임 | 내부 업무 자동화·데이터 처리 |
| `node_web` | JavaScript | 승인 Node.js 런타임 | 간단한 웹·API |
| `typescript_web` | TypeScript, 필요한 설정용 JavaScript | 승인 Node.js 런타임 | 웹 서비스·유지보수 대상 시스템 |

Java, Go, PHP, Ruby, C#, Rust는 기본 금지다. 예외는 프로젝트의 정책 파일을 직접 수정하는 방식이 아니라, 사유·기간·승인자가 있는 기관 승인 예외 번들로만 허용한다.

실제 검사는 확장자만 보지 않는다. 변경 파일, 의존성 매니페스트, 잠금 파일, 런타임 선언, `package.json` 스크립트, Python 실행 선언, Dockerfile, CI 워크플로, Makefile을 함께 검사해야 한다.

## 5. 패키지와 체커의 역할

새 패키지 설치는 AI가 직접 `npm install` 또는 `pip install`을 실행하는 방식으로 허용하지 않는다. `gg package add <패키지>@<버전>` 또는 설치된 하네스 화면의 같은 기능을 통해서만 다음을 수행한다.

1. 승인 레지스트리·대체 패키지·금지 패키지 확인
2. 체커의 패키지·취약점 검증 호출
3. 라이선스·lifecycle script·설치 범위 확인
4. 승인된 잠금 파일 변경과 증적 기록
5. 설치 후 전체 의존성 재점검

개발 중 MCP는 AI가 코드 조각이나 프로젝트를 점검하도록 돕는 조언 경로다. 커밋·CI·이관 전에는 항상 문서화된 `gvskb` CLI를 사용한다.

## 6. 설치·업데이트 신뢰 경계

GitHub `main` 변경은 곧바로 사용자 PC에 적용되지 않는다. 다음 흐름을 확정한다.

`GitHub 소스 변경 -> 테스트·적대적 검증 -> 승인 태그 -> 기관 빌드 -> 코드서명된 승인 번들 -> 포털 다운로드 또는 승인 릴리스 자산 -> 사용자 설치·업데이트`

승인 번들은 하네스 실행기, 체커 번들, 정책, 어댑터 템플릿, Git 훅 템플릿, 버전 manifest를 포함한다. 설치기와 `gg doctor`는 서명, 모든 파일 해시, 폐기 목록, 최소 허용 버전을 검증한다.

상태는 네 가지로만 표시한다.

| 상태 | 사용자 안내 | 활성 기능 |
|---|---|---|
| 미설치 | 공식 설치가 필요합니다. | 설치 |
| 최신 | 최신 버전입니다. | 상태 확인 |
| 업데이트 필요 | 새 승인 버전이 있습니다. | 업데이트 |
| 복구 필요 | 공식 설치본을 확인할 수 없습니다. | 공식 복구 설치 |

다운그레이드는 최소 허용 버전과 폐기 목록을 만족하는 승인 번들에만 허용한다. 자동 복구 전에는 기존 프로젝트와 설정을 백업한다.

## 7. 구현 경계

### 7.1 이 저장소가 구현할 것

- `gg` 실행기와 Windows 설치용 번들 계약
- 정책·언어·런타임·패키지·설계·증적 검증
- Codex·Claude Code 어댑터 생성과 적용 상태 검증
- 프로젝트용 Git 훅과 기관 CI 재사용 workflow
- 체커 CLI·MCP 연계 계약
- 설계 질문, 화면 시안 생성, 확인 영수증

### 7.2 별도 구성요소가 맡을 것

| 구성요소 | 책임 |
|---|---|
| 경기도 바이브 코딩 지원 포털 | 설치 파일 다운로드, 버전 안내, 승인 번들 목록, 일반 사용자 안내, 통합 관리자용 점검 메타데이터 조회 |
| Windows 설치기와 `gg` 하네스 | 설치, 업데이트 확인, 프로젝트 선택, 로컬 체커 실행, 결과 저장, AI 도구 어댑터 적용 |
| `vibecode-checker` | 코드·의존성·룰셋 보안 검사와 보고서 생성 |
| 기관 Git 서비스 | CI 실행, 브랜치 보호, 병합 승인 |

포털은 브라우저만으로 PC 파일을 읽거나 하네스를 강제하지 않는다. 사용자가 실행한 코드서명 설치기와 설치된 `gg` 하네스가 그 역할을 맡는다.

### 7.3 결과와 관리자 접근

개발자는 자신의 PC에서 체커의 HTML·JSON 보고서를 확인해 수정해야 한다. 다른 일반 사용자는 타인의 결과를 볼 수 없다. 포털의 통합 관리자(보안팀)만 중앙에 전송된 최소 점검 메타데이터를 조회한다.

기본 전송 항목은 익명 설치 ID, 하네스·체커 번들 버전, 점검 시각, 점검 종류, 완료·차단·불완전 상태, 심각도·규칙별 집계 수, 승인 번들 ID다. 프로젝트 경로, GitHub URL, 사용자 프롬프트, 원본 소스, 압축파일, 보고서 본문, 코드 줄 위치는 전송 금지다.

상세 보고서가 보안팀 검토에 꼭 필요한 경우에도 자동 업로드하지 않는다. 사용자가 별도로 선택한 보고서에 대해 개인정보·비밀값 제거, 암호화, 보존 기간, 열람 권한을 적용하는 별도 절차를 마련한 뒤에만 허용한다.

| Codex 적용 | 지침 파일 중심 | 적용 상태 검증과 공통 Git/CI 강제 | P1 |
| 패키지 게이트 | 정책만 존재 | 승인·위험·예외 판정 계약 | P0 |
| Git 훅 | 단순 pre-commit | 기존 훅 공존, 실행기 무결성, 실제 commit 시험 | P0 |
| CI·보호 브랜치 | 미구현 | Windows runner, 승인 번들 검증, 필수 검사 | P0 |
| 승인 번들·서명·업데이트 | 정책만 존재 | 키 보관·교체·폐기·anti-downgrade | P0 |
| Windows 설치 패키지 | 미구현 | per-user 설치, 내장 런타임, 복구·제거 | P0 |

P0이 완료되기 전에는 "기관 공통 강제 배포"라고 표현하지 않는다. P1까지 완료되면 제한된 부서의 신규 프로젝트 파일럿을 시작할 수 있다.

## 9. 구현 완료 판정

다음 시나리오가 모두 자동 테스트와 실제 Windows PC 시험을 통과해야 한다.

1. Python·Node.js·Git이 없는 Windows PC가 설치 파일 하나로 하네스와 체커를 설치한다.
2. Codex만 사용하는 사용자와 Claude Code만 사용하는 사용자가 같은 TypeScript 정책을 적용받는다.
3. 설계 질문에서 DB·관리자·외부 API가 필요 없으면 해당 기능이 생성되지 않는다.
4. DB·관리자·개인정보·외부 연계가 필요하면 화면 시안 확인 전 구현 명령이 중단된다.
5. Go 파일, 비허용 Dockerfile·CI 런타임, 직접 패키지 설치가 명확한 이유와 대안과 함께 차단된다.
6. 기존 훅·Claude 설정이 있는 프로젝트에서 손실 없이 병합 또는 명시적 미적용 상태가 표시된다.
7. `--no-verify` 로컬 우회 후에도 PR CI가 같은 검증을 재실행해 병합을 막는다.
8. 악성 `npm test`, `postinstall`, 외부 네트워크 호출이 격리·승인 없이 현재 사용자 권한으로 실행되지 않는다.
9. 체커 미설치, 검사 실패, 불완전 검사, 공식 차단 결과가 각각 구분되어 표시된다.
10. 승인되지 않은 번들, 위변조된 실행기, 취약한 이전 버전은 설치·업데이트·롤백할 수 없다.

## 10. 구현 전 고정 원칙

- 체커는 수정하지 않는다.
- 원본 소스, 압축파일, 체커 보고서 본문은 사용자 PC 밖으로 전송하지 않는다.
- 사용자 PC와 하네스 버전 정보는 최소 메타데이터만 기관 포털로 전송할 수 있으며, 전송 항목과 보존 기간을 별도 승인한다.
- 설치·업데이트·MCP 설정 변경은 항상 사용자에게 대상·변경 위치·결과·복구 방법을 보여준다.
- 진행 창은 완료 시 반드시 "완료" 또는 "실패"와 다음 행동 버튼 하나 이상을 표시한다.
- 설계 지원은 문서만 많이 만드는 방식이 아니라, 필요한 질문과 확인할 화면만 보여주는 방식으로 구현한다.
