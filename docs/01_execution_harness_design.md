# 실행형 바이브코드 하네스 설계

> 문서 역할: 목표 아키텍처와 개발 흐름. 일반 공무원용 Windows 설치·포털·개인정보·관리자 접근 기준은 `docs/09_windows_harness_implementation_baseline.md`가 우선한다. 현재 구현 상태는 README와 `docs/09`의 현황 표를 기준으로 하며, 이 문서의 미래 명령은 구현 완료를 뜻하지 않는다.

## 1. 목적과 범위

바이브코드 하네스는 공무원이 Codex 또는 Claude Code로 업무 도구를 만들 때, 공통 정책으로 설계·구현·테스트·보안 점검·이관 준비를 수행하게 하는 실행형 하네스다. 목표는 AI 도구를 하나로 통일하는 것이 아니라 **어떤 도구를 쓰더라도 같은 개발 언어·환경·증적 기준을 적용하는 것**이다.

이 하네스는 체커 자체가 아니다. `vibecode-checker`의 판정을 호출하고, 결과에 따라 개발·패키지·릴리스 흐름을 진행 또는 중단한다.

## 2. 단일 정책 원본

`shared/harness-core.yaml`과 기관별 `institution-profile.yaml`만 정책 원본으로 유지한다. `AGENTS.md`, `CLAUDE.md`, Claude Hook, Git 훅, CI 워크플로는 이 원본에서 생성되는 산출물이다.

이 원칙은 현재 Codex와 Claude 파일의 TypeScript 허용 여부가 달라진 문제를 제거한다. 어댑터 파일을 사람이 각각 고치지 않고 `gg adapter generate`와 `gg adapter verify`로 동기화한다.

## 2.1 기존 하네스에서 계승할 장점

| 계승 대상 | 유지할 장점 | 새 하네스에서의 정리 방식 |
|---|---|---|
| Codex 중심 하네스 | 기관 프로파일, 승인 언어·런타임, 체커·패키지 게이트, 성숙도별 검증 | `shared/harness-core.yaml`과 `institution-profile.yaml`의 단일 정책 원본 |
| Claude 역할형 하네스 | 업무 접수·설계·구현·검증·릴리스 역할 구분, 세부 스킬, Hook 자동화 가능성 | 다섯 역할과 여섯 스킬로 압축하고 L2/L3에서만 역할을 분리 |
| 두 하네스 공통 | 골든 템플릿, 사용자 시나리오, 증적 기록, 사람 승인 경계 | `gg init`, `gg design`, `gg verify`, `gg release`의 공통 산출물 계약 |

기존 역할·스킬 문서를 즉시 폐기하지 않는다. 새 여섯 스킬의 내부 참고 자료로 옮기고, 동일 기능을 두 지침 파일에 중복 작성하지 않는다.

## 3. 역할과 스킬

### 3.1 역할: 다섯 개, 항상 동시에 실행하지 않음

| 역할 | 책임 | 기본 적용 |
|---|---|---|
| Intake | 업무 목적, 사용자, 입력·출력, 위험 신호 확인 | 항상 |
| Architect | 성숙도, 화면, DB, 관리자, 트랙·런타임 결정 | 신규 기능·구조 변경 |
| Builder | 승인된 화면·기능 구현 | 구현 요청 |
| Verifier | 테스트, 패키지 게이트, 체커, 시나리오 검증 | L2 이상 또는 위험 변경 |
| Release | 보고서, SBOM, 이관·배포 준비 | L3 이상 |

L1에서는 Codex 또는 Claude Code의 주 에이전트가 역할을 순서대로 수행한다. L2에서 Verifier, L3에서 Release만 필요할 때 분리한다. 전문 역할을 매번 병렬 호출하지 않아 시간·토큰·문서 과잉을 줄인다.

### 3.2 공통 스킬: 여섯 개

| 스킬 | 포함하는 기존 세부 작업 | 산출물 |
|---|---|---|
| `gg-start` | 인터뷰, 성숙도, 트랙 선택 | 업무 요약, 작업 현황, 화면 목록 |
| `gg-plan` | PRD, 화면·기능, DB 초안 | 설계 묶음 |
| `gg-build` | 템플릿, 신규 구현, 변경 구현 | 실행 가능한 소스 |
| `gg-package` | 패키지 정책, 대체안, 예외 경로 | 패키지 판정 기록 |
| `gg-verify` | 테스트, 시나리오, 체커, 적대적 검증 | 검증 결과 |
| `gg-release` | 보고서, SBOM, 이관·승인 준비 | 릴리스 증적 |

## 4. 언어와 실행 환경

### 4.1 기본 허용 범위

- Python: 내부 업무 웹, 자동화, 데이터 처리
- JavaScript: Node.js API, 정적 웹, 브라우저 기능
- TypeScript: 승인된 Node.js·React/Vite 트랙의 구현 소스

Java, Go, PHP, Ruby, C#, Rust 등은 기본 금지다. 필요한 경우 하네스가 임의로 추가하지 않고 `needs-review`로 전환한다.

### 4.2 실제 통제 방식

1. `gg init`은 승인 템플릿과 해당 런타임의 버전을 `harness.lock`에 기록한다.
2. `gg build`는 변경된 소스 확장자, 런타임 선언, 의존성 manifest를 검사한다.
3. `gg verify`는 비허용 언어·미승인 패키지·런타임 불일치를 실패 코드와 함께 반환한다.
4. Git 훅은 기본 커밋·푸시를 막고, CI는 우회된 로컬 훅까지 최종 차단한다.

### 4.3 신뢰와 정책 무결성

`harness.lock.json`은 단순 버전 메모가 아니다. 승인 번들 ID, 정책 해시, 서명 키 ID, 허용 언어, 런타임, 생성 어댑터 버전을 기록한다. `gg verify`와 CI는 승인 manifest의 서명·해시와 lock을 비교한다. GitHub `main`을 직접 pull해 운영 하네스를 바꾸지 않는다.

이전 버전으로의 롤백은 이전 정상 번들이면서 최소 허용 버전과 폐기 목록을 통과할 때만 허용한다. 자세한 키 교체·폐기·다운그레이드 방지 규칙은 `shared/policies/trust-and-integrity.yaml`을 따른다.

## 5. 통제 수준

| 수준 | 대상 | 강제 내용 |
|---|---|---|
| GUIDED | L0~L1 | 화면 확인, 위험 변경 quick 점검, 업무 언어 안내 |
| ENFORCED | L2 | `harness.lock`, Git 훅, `gg verify`, 패키지 게이트, 표준 점검 |
| RELEASE_LOCKED | L3 | PR 보호, CI 필수 검사, 전체 점검, HTML·JSON 보고서, SBOM, 사람 승인 |

로컬 지침이나 Hook은 편의성과 빠른 피드백을 위한 첫 방어선이다. 원시 터미널 또는 다른 편집기를 통한 우회 가능성은 GitHub 보호 규칙과 CI가 최종적으로 막는다.

`gg verify`는 프로젝트가 선언하지 않은 임의 명령을 실행하지 않는다. 미검증 프로젝트를 처음 열 때 테스트·네트워크·생성 스크립트 실행은 사용자에게 보이고 승인받는다. CI는 비밀값 없이 격리된 환경에서 같은 검증을 다시 실행한다.

## 6. 실행 명령 계약

| 명령 | 사전 조건 | 성공 기준 | 실패 시 다음 행동 |
|---|---|---|---|
| `gg init` | 프로젝트 경로, 사용할 도구 선택 | 정책·어댑터·템플릿·훅 설치 | 설치 원인 표시 후 재시도 |
| `gg start` | 업무 설명 | 화면 목록·위험·성숙도 결정 | 필요한 업무 질문만 추가 |
| `gg design` | 화면 목록 | 화면 시안과 기능·데이터 결정 | 사용자 확인 전 구현 보류 |
| `gg build` | 확인된 설계 | 승인 언어·런타임 안의 실행 소스 | 정책 불일치 시 트랙 변경 또는 검토 |
| `gg verify` | 실행 가능한 소스 | 테스트·시나리오·체커 통과 | 실패 항목 수정 후 재검증 |
| `gg release` | `gg verify` 통과 | 보고서·SBOM·승인 요청 증적 | 누락된 증적을 명시 |

## 7. 기록과 재검증

모든 단계는 `evidence/work-status.json`에 시작·완료 시각, 사용 도구, 적용 정책 버전, 실행 명령, 결과, 체커 프로필, 실패 코드만 기록한다. 원본 소스·비밀값·보고서 본문은 기록 파일에 넣지 않는다.

커밋 전에는 `gg verify --changed`, 배포·이관 전에는 `gg verify --full`을 실행한다. CI는 로컬 결과를 신뢰하지 않고 깨끗한 환경에서 같은 명령을 재실행한다.

## 8. 단계별 구현 계획

| 단계 | 구현 범위 | 완료 기준 |
|---|---|---|
| 0. 정책 정렬 | 공통 정책, 기관 프로파일, 역할·스킬 매핑, 기존 문서 이관 표 | Codex·Claude 언어·런타임 판단이 동일 |
| 1. 최소 실행기 | `gg init`, `gg doctor`, `gg verify` | 새 프로젝트에 양쪽 어댑터와 공통 검증이 설치됨 |
| 2. 설계 우선 흐름 | `gg start`, `gg design`, 화면 시안·DB·관리자 질문 기록 | 시안 확인 전 복잡한 구현이 시작되지 않음 |
| 3. 강제 연결 | Claude Hook, Git 훅, CI 재사용 workflow | 우회된 로컬 훅도 PR CI에서 차단됨 |
| 4. 릴리스 연결 | `gg release`, 체커 최종 보고서, SBOM, 승인 번들 manifest | 사람 승인 전 기관 배포 번들이 생성되지 않음 |

각 단계는 대표 Python, JavaScript, TypeScript 프로젝트를 Codex와 Claude Code 각각에서 실행해 같은 정책 결과가 나오는지 적대적으로 검증한다.
