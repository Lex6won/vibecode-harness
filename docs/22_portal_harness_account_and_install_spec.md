# 포털 계정·하네스 설치 최종 명세

## 목적

사용자는 비밀번호, PowerShell 명령, Node/Python/체커 설치를 이해하지 않아도 하네스를 사용할 수 있어야 한다. 포털은 이메일 기반 개인 계정, 서버 체커, 보고서, 배포를 제공하고 하네스는 개발 PC의 프로젝트 설정을 적용한다. 협업 작업공간이나 부서 공용 계정은 제공하지 않는다.

## 계정과 저장 정보

포털은 다음 정보를 저장한다. 프로젝트 소스는 사용자가 서버 체커 점검을 명시적으로 요청하고 범위를 확인한 경우에만 전송·처리한다. 하네스 상태 보고에는 프로젝트 소스나 로컬 경로를 포함하지 않는다. 프롬프트, AI 도구 토큰·쿠키·비밀번호, 개인키, 환경변수는 저장하거나 전송하지 않는다.

| 정보 | 저장 여부 | 목적 | 변경 규칙 |
|---|---|---|---|
| 이메일 주소 | 저장 | 이메일 인증, 로그인 링크 발송, 본인 점검 이력 조회, 보안 안내 | 기존·새 이메일 모두 인증한 뒤 변경한다. 기존 주소에 접근할 수 없는 경우에는 별도 계정 복구 절차를 사용한다. |
| 이메일 인증 상태·시각 | 저장 | 계정 본인 확인과 보안 감사 | 사용자가 임의 변경하지 않는다. |
| 기관명 | 저장 | 개인 보고서와 이용 현황의 현재 소속 표시 | 프로필에서 언제든 수정할 수 있다. |
| 부서명 | 저장 | 개인 보고서와 이용 현황의 현재 소속 표시 | 프로필에서 언제든 수정할 수 있다. |
| 기관·부서 변경 이력 | 저장 | 보고서의 출처와 보안 감사 | 변경 전후 값, 시각, 계정 ID만 기록한다. |
| 보고서 생성 시점의 기관·부서 스냅샷 | 저장 | 과거 보고서의 당시 맥락 보존 | 현재 프로필 수정으로 바꾸지 않는다. |
| 하네스 상태 요약 | 선택 동의 후 저장 | 설치 상태, 버전, 적용 도구, doctor 요약 표시 | 기기 연결 해제 또는 계정 삭제 시 삭제한다. |
| 점검 요청에 사용자가 선택한 소스 | 점검 요청 시에만 전송·처리 | 서버 체커 분석과 보고서 생성 | 전송 전 범위·보관 기간을 표시하고 동의를 받는다. 기본 정책은 분석 후 원본 삭제이며, 보고서는 별도 보관 정책을 적용한다. |

기관명과 부서명은 이메일 인증만으로 실제 소속을 증명하지 않는다. 화면에는 “사용자가 등록한 소속 정보”로 표시하며, 공식 소속 확인이나 부서 공동 권한에 사용하지 않는다.

## 포털 로그인

포털은 비밀번호를 사용하지 않는다.

```text
이메일 입력
  -> 일회용 이메일 인증/로그인 링크 발송
  -> 링크 클릭
  -> 포털 로그인 및 계정 생성 또는 기존 계정 접속
```

- 링크는 1회만 쓸 수 있고 10~15분 후 만료한다.
- 인증 링크 사용 뒤에는 사용 중인 브라우저에서 로그인 상태를 유지한다.
- 새 브라우저·새 기기·로그아웃 상태에서만 이메일 인증 링크를 다시 사용한다.
- 기기에서 더 간단한 인증 수단을 등록하는 기능은 선택적으로 제공할 수 있으나, 첫 화면에서 어려운 기술 용어를 강요하지 않는다.
- 로그인 링크 요청 횟수 제한, 봇 방어, 로그인·이메일 변경·기기 연결 해제 감사 로그를 적용한다.

최초 등록 화면에서 받는 입력은 아래 세 가지뿐이다.

```text
이메일
기관명
부서명
```

기관명과 부서명을 프로필 수정 화면에서 바꿀 수 있게 한다. 이메일 변경은 계정 탈취 방지를 위해 기존 주소와 새 주소의 인증을 모두 요구한다.

## 포털의 역할

포털은 개발 PC의 파일을 직접 수정하거나 AI 도구를 실행하지 않는다.

- 이메일 인증, 계정·프로필·점검 이력 관리
- 서명된 Harness Manager EXE의 다운로드와 업데이트 정보 제공
- 사용자가 명시적으로 제출한 점검 대상에 대해 서버에 설치된 체커 실행
- 점검 요청 수신, 처리 상태, 보고서 표시
- 사용자가 동의한 하네스 설치·버전·doctor 요약 표시
- 이메일·기관명·부서명 수정, 기기 연결 해제, 계정 삭제

포털 체커는 서버에서만 운영한다. 사용자 PC에는 체커 실행 파일이나 Python을 설치하지 않는다. 소스는 자동 전송하지 않으며, 사용자가 점검을 요청할 때 선택한 범위만 전송한다. 점검 결과가 오기 전에는 `점검 요청됨` 또는 `분석 중`만 표시하고, `승인됨`으로 표시하지 않는다.

## 하네스의 역할

하네스는 사용자의 개발 PC와 선택한 프로젝트 폴더에서만 동작한다.

- 서명된 EXE 설치, 업데이트 확인, 복구·제거
- Codex, Claude Code, Google Antigravity의 설치 여부 감지
- 프로젝트 폴더 선택
- 선택한 도구의 지침, 훅, 플러그인 적용
- 기존 설정의 백업, 안전한 병합, 복구
- 로컬 정책·설정 상태 확인
- 사용자 동의 후 포털에 최소 상태 전송
- 사용자가 점검 범위와 보관 정책을 확인한 뒤에만 서버 체커 점검 요청·소스 제출

하네스는 AI 도구의 로그인 정보, 토큰, 쿠키, 비밀번호를 읽거나 포털에 보내지 않는다. 이미 로그인된 AI 도구는 그 상태로 사용하며, 하네스는 필요한 프로젝트 설정만 적용한다. 프로젝트 소스는 사용자가 서버 점검을 요청한 경우에만, 선택한 범위와 보관 정책을 확인한 뒤 포털로 전송한다.

## 하네스 설치와 프로젝트 적용 화면

EXE 설치 후 Harness Manager를 자동 실행한다. 설치 자체에서는 AI 도구를 고르게 하지 않고, 프로젝트별로 도구를 선택하게 한다.

```text
VibeCode Harness

프로젝트 폴더
[ C:\\work\\my-project                         ] [변경]

감지된 AI 도구
☑ Codex
☑ Claude Code
☐ Google Antigravity

[이 프로젝트에 적용]
```

AI 도구는 자동 감지해 기본 선택한다. 사용자는 필요 없는 도구만 해제한다. Codex, Claude Code, Antigravity는 한 프로젝트에 복수로 적용할 수 있다.

## 도구 선택 변경

도구 선택은 나중에 반드시 바꿀 수 있어야 하며, 변경은 해당 프로젝트에만 적용한다.

```text
내 프로젝트

프로젝트: C:\\work\\my-project
적용된 도구: Codex, Claude Code

[도구 선택 변경] [상태 확인] [하네스 설정 복구]
```

| 변경 | 처리 |
|---|---|
| 도구 추가 | 해당 도구의 하네스 지침·보조 파일·훅·플러그인을 적용한다. |
| 도구 해제 | 하네스가 소유한 항목만 제거하거나 백업한다. 사용자 원본 설정은 제거하지 않는다. |
| 기존 설정 발견 | 변경 전 백업하고 병합 가능한 항목만 자동 반영한다. 충돌은 사용자 확인 화면에 표시한다. |
| 변경 실패 | 기존 상태로 되돌리고 복구 방법을 안내한다. |

구현에는 도구 설정을 다시 적용·제거·복구하는 명령 계층이 필요하다.

```text
gg configure --project <폴더> --tools codex,antigravity
gg configure --project <폴더> --remove claude
gg restore --project <폴더> --backup <백업번호>
```

일반 사용자는 이 명령을 입력하지 않는다. Harness Manager가 내부에서 실행한다.

## 현재 구현과 필요한 변경

현재 `gg init`은 Codex, Claude Code, Antigravity의 복수 선택과 `all` 선택을 지원한다. 그러나 시작 메뉴는 콘솔 기반 `gg init --interactive`를 열며, 이미 초기화된 프로젝트의 도구 선택 변경은 지원하지 않는다.

공식 EXE 배포 전에는 다음을 구현한다.

1. 콘솔 질문 대신 Harness Manager GUI에서 폴더·도구를 선택한다.
2. `gg configure`와 `gg restore`로 추가·해제·복구를 지원한다.
3. 도구별 파일의 소유권과 백업 정보를 기록해 사용자 설정을 보존한다.
4. 서버 체커 모델에 맞게 사용자 EXE의 체커·Python 의존성을 제거하고, `doctor`는 포털 연결과 로컬 설정 상태를 확인하게 바꾼다.
5. 포털 연동은 명시 동의와 최소 상태 전송 원칙을 적용한다.

## 완료 기준

- 사용자는 비밀번호 없이 이메일 인증만으로 가입·로그인할 수 있다.
- 이메일, 기관명, 부서명은 프로필에서 확인·수정할 수 있다.
- 과거 보고서는 생성 당시의 기관·부서 정보를 유지한다.
- 사용자는 EXE 설치 뒤 프로젝트 폴더와 도구만 선택해 적용할 수 있다.
- 세 AI 도구를 복수 선택할 수 있고, 프로젝트별로 나중에 추가·해제할 수 있다.
- 기존 사용자 설정은 삭제되지 않고 백업·복구할 수 있다.
- 체커는 포털 서버에서 실행되며 사용자 PC에 체커 설치를 요구하지 않는다.
- 상태 보고에는 프로젝트 소스·경로·AI 자격증명을 포함하지 않는다. 소스는 사용자가 서버 점검을 명시적으로 요청한 경우에만 선택 범위를 전송한다.

### 2026-08-28 (2차) — 체커 번들 원칙 개정 + 구현 확인 결과 반영

**개정 (사용자 확정):** "공식 EXE 배포 전 구현 4번(사용자 EXE의 체커·Python 의존성 제거)"을 다음으로 대체한다.

> **최종 보안 점검은 포털(서버 체커)에서 수행한다.** 사용자 PC의 하네스는
> 패키지 사전확인(`gg package check`)과 개발 중 검증에 쓰는 **체커를 번들로 유지**한다
> — 오프라인에서도 패키지 도입 전 확인이 가능해야 하기 때문이다.
> `doctor` 는 로컬 설정 상태를 확인하고, 상태 보고 연동이 구현되면 포털 연결도 확인한다.

근거: 하네스 `gg verify` 가 최종 판단을 `ready_for_portal_scan`(포털 점검 필요)으로
넘기는 구현이 이미 완료되어, 서버 체커 모델과 로컬 사전확인이 역할로 분리되었다.

**구현 확인 결과 (2026-08-28 포털 측 검증):**

- 지원 도구는 6종으로 확대 확인: Codex · Claude Code · Google Antigravity ·
  Claude Desktop · ChatGPT Desktop · Lovable(+GitHub). 본문 3종 목록을 대체한다.
- Lovable 은 `typescript_postgres`(JavaScript·TypeScript·PostgreSQL 공통형) 프로파일 + GitHub
  PR 게이트 전제로 동작한다. Supabase 는 기본이 아니라 선택 통합(legacy 별칭)이다.
  Lovable·Supabase 의 공공 실사용 허용 여부는 보안부서 정책 확인 대기 —
  확인 전까지 포털 안내 화면에는 지원 도구로 표기하지 않는다.
- `gg configure --tools/--remove`(도구 추가·해제)와 Harness Manager GUI(manager.ps1,
  EXE 실행 후 화면)는 구현 확인. `gg restore`(백업 복구 명령)는 미구현 — 잔여 작업.
- 하네스의 "pilot portal"(GitHub Pages)은 EXE 화면이 아니라 **별도 웹 배포 페이지**다
  (파일럿 한정 임시 채널). 정식 단계에는 보안 게이트 포털이 하네스의
  `release-index.json` 계약(installer_published·SHA-256·서명 상태)을 소비해
  배포 창구를 포털로 일원화한다.
