> 각 도구의 개발 세션(사람·AI 모두)에 이 문서를 그대로 전달해 온보딩에 쓴다.

## 1. 최종 목표 — 도구가 아니라 활성화

이 사업의 목표는 보안 도구를 만드는 것이 아니다.

**체커와 하네스를 누구나 쉽게 사용하게 해서, 바이브코딩(AI 코딩) 하는 사람과
보안성 검토하는 사람을 모두 편리하게 하고, 그 결과 바이브코딩을 활성화하는 것이다.**

구조는 선순환이다:

1. 안전하게 개발할 수 있는 **기준**을 만든다 → **하네스**
2. 그 기준으로 개발·점검한 **실적**(점검 결과, 패키지 사용 근거)을 모은다 → **체커 + 포털**
3. 실적에 기반해 점점 더 안전하고 편리하게 개발할 수 있는 **환경**을 만든다 → **레지스트리(화이트리스트)**
4. 환경이 좋아질수록 더 많은 사람이 안심하고 바이브코딩을 한다 → 1로 순환

안 쓰이는 보안 도구는 효과가 0이다. 어떤 개선이든 "더 쓰게 되는가"에 기여해야 한다.
단, 그 기여 방식은 도구마다 다르다 — 아래 2절이 그 구분이다.

## 2. 도구별 품질 기준 — 서로 다른 것이 정상

| 도구 | 역할 | 품질 기준 | 타협 금지선 |
|---|---|---|---|
| **체커** (vibecode-checker/gvskb) | **관측** — 사실만 말한다 | **보안적 완벽.** 오탐·미탐을 끝까지 잡는다 | 편의를 이유로 검사 수준을 낮추지 않는다. "확인 못 함"을 "안전"으로 보고하지 않는다 |
| **하네스** (vibe_harness) | **집행** — 기준을 지키게 한다 | **이탈 방지 + 조력.** 개발자가 틀을 벗어나지 않게 잡아주고, 벗어나려 할 때 안전한 길을 안내한다 | 막기만 하고 돕지 않으면 실패다. 우회로를 열어주는 편의도 실패다 |
| **포털** (security-gate-portal) | **전달·축적** — 사람을 잇는다 | **편의.** 개발자·검토자 양쪽이 쉽게 쓰는 것 자체가 품질 | 체커 산출물을 재가공·재해석하지 않는다. 판정을 완화하는 자동 로직을 두지 않는다(강화는 자동, 완화는 사람) |
| **보안부서** (사람) | **판정** | — | 승인·차단 판정은 오직 사람이 한다. 어떤 도구도 대신하지 않는다 |

각 도구의 설계 판단은 **그 도구의 기준**으로 한다.
포털에서 "더 엄격하게"는 답이 아니고, 체커에서 "더 편하게"도 답이 아니다.
세 도구는 분리해서 개발·보완하되, 최종 목표를 향해 지속적으로 개선·운영한다.

## 3. 판정과 데이터의 흐름 — 연동 시 지켜야 할 구조

```
개발자 PC                          서버                         사람
┌────────────┐              ┌──────────────┐            ┌──────────┐
│  하네스     │─ 점검 요청 ─▶│ 체커(관측)     │            │ 보안부서   │
│ (집행)      │◀─ verdict ──│               │            │ (판정)    │
└────────────┘              │ 포털(전달·축적) │─ 근거 제공 ─▶│          │
                            │               │◀─ 판정 ─────│          │
                            └──────┬───────┘            └──────────┘
                                   │ 판정 반영
                                   ▼
                            레지스트리(화이트리스트)
                                   │ 체커가 참조
                                   └────▶ verdict에 실려 하네스로 복귀
```

- **하네스는 항상 체커에게 묻는다.** 레지스트리·화이트리스트를 직접 조회하지 않는다.
  기관 판정은 체커의 verdict(`registry_approved`/`registry_rejected` 등)에 실려 돌아온다.
- **체커의 verdict 사다리**(엄격한 순): malicious > registry_rejected > … >
  registry_approved > checked_clean > unknown. 체커는 사실과 판정 근거만 싣고,
  스스로 승인하지 않는다.
- **포털은 판정을 보수적 방향으로만 바꿀 수 있다**(예: allow → incomplete).
  완화(needs_review → allow)는 절대 자동으로 하지 않는다.
- **화이트리스트 근거 축적**: 포털이 점검마다 패키지 메타값(이름·버전·CVE·KEV·라이선스·
  기관판정 등 허용목록 필드만, 소스·경로·개인정보 금지)을 모아 보안부서에 제공한다.
  보안부서 판정 → 레지스트리 번들 → 체커 참조로 순환이 닫힌다.

## 4. 도구 간 연동 지점 (현재 합의된 것)

| 연동 | 방향 | 상태 |
|---|---|---|
| 점검 실행 | 포털 → 체커 CLI (`gvskb scan --check-deps`) | 운영 중 |
| SBOM 생성 | 체커 `--sbom` (CycloneDX 1.6) → 포털이 저장·전달 | 체커 기능 완비, 포털 플래그 추가 예정 |
| PC 상태 보고 | 하네스(설치·doctor·verify 시점) → 포털 서버, opt-in | 설계 합의(포털 docs/23 `clients/report`), 하네스 측 구현 협의 필요 |
| 패키지 사전 확인 | 하네스 `gg package check` → 체커 | 운영 중 |
| 기관 판정 전달 | 레지스트리 번들 → 체커 verdict → 하네스 | 구조 확정, 번들은 보안부서 판정 축적 후 |
| 도구 설치 | 포털=안내·배포 / 도구관리자(PC)=버전·업데이트 UI / 하네스=실제 감지·설정 | 3층 분리 합의 (도구관리자 실행체는 코드서명 확정 후) |

## 5. 하네스 적용 대상 (로드맵)

현재: Claude Code, Codex CLI.
목표: Claude 데스크톱, ChatGPT 데스크톱, Antigravity까지 확대.
포털은 하네스가 실제 지원하는 것만 표기한다 — 앞서 약속하지 않는다(정직 표시 원칙).

## 6. 개선 작업 시 확인 목록

어느 도구를 개선하든 시작 전에 스스로 물을 것:

1. 이 변경은 **어느 도구의 품질 기준**에 속하는 일인가? (2절 표)
2. 역할 경계를 넘지 않는가? (관측이 판정을 하려 하거나, 집행이 우회로를 열거나,
   전달이 재해석을 하려 하지 않는가)
3. 판정 흐름(3절)의 방향을 거스르지 않는가? (특히: 하네스의 레지스트리 직접 조회 금지,
   포털의 판정 완화 금지)
4. 그 결과 개발자 또는 검토자가 **더 쓰게 되는가?**
